# Engineering and Verification

Kaven Docker follows the shared `kaven-coding-standards` baseline. The native
Rust backend owns durable state, credentials remain in the operating-system
credential manager, and the Vue frontend keeps only in-memory presentation
state.

## Runtime storage

The Windows application root is:

```text
%LOCALAPPDATA%\Kaven\Kaven-Docker\
```

Existing release-candidate installations using the legacy lowercase
`kaven-docker` directory are moved to the canonical directory on first start
when the canonical directory does not already exist. `config.json` is the one
versioned authoritative configuration source. Configuration writes use
same-directory temporary files, file synchronization, and atomic replacement.
The pre-release three-file layout is migrated through a durable journal; the
verified legacy files are retained under `recovery/config-v0-backup/` for
downgrade recovery. Import files and stored settings have explicit byte and
item limits and reject unknown fields.

The authoritative configuration contract is:

```json
{
  "schemaVersion": 1,
  "appSettings": {},
  "proxyProfiles": [],
  "registries": []
}
```

The three top-level sections contain the corresponding backend API models.
Unknown fields and unsupported schema versions are rejected without mutation;
password values never appear in this file. User-initiated exports wrap the
same sections with `appId: "kaven-docker"` and
`bundleKind: "configuration"` so imports can reject data for another product.

The locale is part of backend-owned application settings. Browser Local
Storage, Session Storage, IndexedDB, and Cache Storage are not persistence
layers for this application.

Synchronization logs are capped at 10 MiB each and retain at most 20 files.
The reproducible content-addressed Blob cache is capped at 20 GiB and is
reduced to 18 GiB, oldest first, before a new synchronization starts.

Automatic-update scheduling state is stored separately in `state.json` under
the application root. Successful automatic checks are limited to once every
24 hours; failures retry with bounded exponential backoff. The signed update
manifest is fetched only through `public.data.kaven.xyz`; installer URLs in
that manifest may use GitHub Releases or another host. Update installation is
mutually exclusive with image synchronization.

## Local verification

Install the locked dependency graph first:

```powershell
npm ci
```

Then run:

```powershell
npm run lint
npm run typecheck
npm test
npm run test:audit-policy
npm run build
cargo fmt --manifest-path src-tauri/Cargo.toml --all -- --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --all-features -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml
npm run audit:npm
cargo audit --file src-tauri/Cargo.lock
```

Before release, also run `npm run tauri build` on Windows and complete the
installation, upgrade, uninstall, credential-preservation, failed-import, and
interrupted-transfer recovery checks in [RELEASE.md](RELEASE.md).

## Generated schemas

Files under `src-tauri/gen/schemas/` are generated by Tauri from the checked-in
capability configuration. Do not edit them manually. After a capability or
Tauri configuration change, regenerate them using the Tauri CLI and verify
that a second generation produces no diff.
